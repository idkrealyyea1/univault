# UniVault — University Resource & Services Platform

A gated academic resource platform. Visitors pick a **university** → **field** → see a dashboard of **services** (homework help, project help, materials). Browsing the dashboard requires **login** (username + password); opening a specific service's files requires **admin-approved access** after an off-platform payment.

Stack: **Netlify** (frontend) + **Render** (Node/Express API) + **Supabase** (Postgres, Auth, Storage).

```
frontend/   → static site (deploy to Netlify)
backend/    → Node.js + Express API (deploy to Render)
supabase/   → SQL to run in the Supabase SQL editor
```

## 2. Deploy steps

### 2.1 Supabase (database + auth + storage)

1. Create a project at [supabase.com](https://supabase.com). Note the **Project URL**, **anon key**, and **service_role key** (Dashboard → Settings → API).
2. Open **SQL Editor** and run, in order:
   - `supabase/schema.sql`
   - `supabase/seed.sql`
   - `supabase/rls.sql`
3. (Optional) Make yourself admin after creating your account:
   - Sign up on the live site normally, then run `supabase/admin.sql` with your username.

### 2.2 Render (backend)

1. Create a **Web Service** pointing at the `backend/` folder of your GitHub repo.
2. Build command: `npm install` · Start command: `node server.js`.
3. Add the environment variables (see `backend/.env.example`):
   - `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`
   - `ADMIN_PASSWORD_HASH` — a **bcrypt** hash of your admin password. Generate locally:
     ```bash
     node -e "console.log(require('bcryptjs').hashSync('YOUR_ADMIN_PASSWORD', 10))"
     ```
   - `JWT_SECRET` — any long random string
   - `ALLOWED_ORIGIN` — your Netlify URL (e.g. `https://your-site.netlify.app`)
   - `VAPID_SUBJECT`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`:
     ```bash
     npx web-push generate-vapid-keys
     ```
4. Note the deployed URL, e.g. `https://univault-api.onrender.com`.

### 2.3 Netlify (frontend)

1. New site from Git → connect the `frontend/` folder.
2. No build command. Publish directory = `frontend`.
3. Edit `frontend/js/config.js`:
   - `SUPABASE_URL`, `SUPABASE_ANON_KEY`
   - `API_URL` = your Render URL
   - `VAPID_PUBLIC_KEY` (same value as the Render env var; public keys are safe to expose)

> **Note:** `frontend/js/config.js` is the single config file. `scripts/dev.sh` overwrites it with local values when testing locally, so production values are restored by re-editing it before deploy (or keep a copy).

## 2.4 Local testing (before any servers) — RECOMMENDED

Everything runs on your machine using the **Supabase CLI + Docker** (no accounts needed).

### Prerequisites

- **Docker** running, and your user in the `docker` group:
  ```bash
  sudo usermod -aG docker $USER
  # then log out and back in (or reboot)
  ```
- **Supabase CLI** — this repo was developed with `v2.111.0`:
  ```bash
  # Download the Linux binary (pick the current release tag from GitHub releases)
  curl -L -o /tmp/supabase.tar.gz https://github.com/supabase/cli/releases/download/v2.111.0/supabase_linux_amd64.tar.gz
  mkdir -p ~/.local/bin && tar -xzf /tmp/supabase.tar.gz -C ~/.local/bin && chmod +x ~/.local/bin/supabase
  ```
- Node 18+ (to run the backend) and python3 (to serve the frontend).

### Run

```bash
./scripts/dev.sh
```

That one command:

1. Starts local Supabase (Postgres + Auth + Storage + API) via Docker — **first run pulls images, takes a while**.
2. Auto-applies the schema/seed/RLS from `supabase/migrations/` (copies of `schema.sql`, `seed.sql`, `rls.sql`).
3. Writes `backend/.env` and `frontend/js/config.js` with the local URLs and keys (generates bcrypt admin hash + VAPID keys on first run).
4. Starts the backend API on `:3000`.
5. Serves the frontend on `:8080`.

Then open:

- **Site:** http://localhost:8080
- **Admin panel:** http://localhost:8080/admin/index.html (password: `admin12345`, printed by the script — change it later in `backend/.env` and re-run the script)

### First test pass

1. On the site, pick **UCAS → Cybersecurity & Information Security Engineering** — you should get the cyber theme (matrix rain, boot sequence) and be redirected to login.
2. Sign up with a username + password.
3. Make yourself admin: `./scripts/make-admin.sh <your-username>` — the **Admin** link then appears in the header.
4. In the admin panel: add a service (or approve a "Service Application"), upload a file under **Resource Files**.
5. Log out, sign up a **second** account, request access on the service, then in the admin panel approve it → the second account now sees **Open** and can download the file.
6. Push notifications work on `localhost` (browsers treat it as a secure context).

To stop everything: Ctrl+C the frontend server, then `kill $(cat .dev-backend.pid)` and `supabase stop`.

## 3. How the security gate works

- **Public (no login):** university list, field list, service titles/prices, popularity counts — plain Supabase reads, allowed by RLS.
- **After login:** the field dashboard. Locked/unlocked state comes from the student's own `access_grants` rows.
- **After admin approval:** the student's `Open` button calls the backend `GET /api/resources/:serviceId`. The backend verifies the `access_grants` row exists, then returns **signed, 10-minute URLs** for the files in the private `resource-files` bucket.

No student can ever:
- list `resources` without a grant (RLS policy),
- create an `access_grants` row (no client insert policy exists; only the backend's service-role key can),
- read the `audit_log` (RLS with zero policies).

The service-role key lives **only** in Render env vars and never in frontend files.

---

## 4. The admin flow (per payment)

1. Student clicks **Request Access** on a locked service → row in `access_requests` (`pending`).
2. They pay you off-platform (bank transfer / cash / WhatsApp).
3. You open `/admin/dashboard.html` → **Access Requests** → **Approve**.
4. Backend inserts into `access_grants`, marks the request approved, and pushes a notification to the student (if subscribed).
5. The service now shows **Unlocked** for that student and returns real download links.

Everything that matters (approvals, signups, resource opens, admin logins) is recorded in `audit_log`, viewable under the **Audit Log** tab.

## 6. Testing checklist before going live

- [ ] RLS tested with a **non-admin** account (can't see resources, can't insert grants).
- [ ] `SUPABASE_SERVICE_ROLE_KEY` only in Render env vars.
- [ ] CORS `ALLOWED_ORIGIN` set to your Netlify domain.
- [ ] Admin login works and rate-limit kicks in after 5 wrong tries.
- [ ] Signup → login → request access → approve → open → download, end to end.
- [ ] Upload a PDF via Admin → Resources, then verify only the grant-holder can fetch it.
- [ ] Push notification received after approving a request (HTTPS required).
- [ ] Zod validation: try a malformed UUID in a URL and oversized form fields → clean 400s, no stack traces.

## 7. Common gotchas

- **Username taken error shows "already registered"?** The synthetic email is `username@univault.local` — it's a username conflict, not an email issue.
- **`service_popularity` empty on the dashboard?** The `grant select` on the view is in `seed.sql` — re-run it if you created the view after RLS.
- **Admin link missing in the header?** Run `supabase/admin.sql` for your account.
- **Signup 429 errors?** The rate limiter allows 5 signups/hour/IP — that's intentional (§9.4).
- **Push on iOS?** Only works when the site is added to the home screen (PWA, iOS 16.4+). Desktop browsers need no setup.
